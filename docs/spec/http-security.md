# HTTP and MCP-over-HTTP security

How `wikirs serve` (`/ops` and `/mcp`) and `wikirs mcp` are protected. Decided in [HTTP and MCP-over-HTTP security](../../.scratch/wikirs/issues/15-http-security.md). The routes are in [interfaces.md](interfaces.md), and the one-Wiki-per-process rule is in [wiki-selection.md](wiki-selection.md).

The MCP Streamable HTTP transport requires servers to validate `Origin` (DNS rebinding), and recommends binding to localhost when local and authenticating. The rules below apply to `/ops` and `/mcp` alike, through one axum middleware.

## Binding

- **Default**: `127.0.0.1` and `[::1]`, port **4747**. `--port 0` picks a free port, and the URL is printed.
- **Non-loopback** `--bind` requires `--allow-remote`; `serve` refuses to start without it. Token auth is then always on (a token is generated if none exists, and printed), and `serve` warns that traffic is unencrypted.
- **No built-in TLS.** Remote access goes through an SSH tunnel, Tailscale or a reverse proxy.

## Authentication

- **`Authorization: Bearer <token>`** covers both `/ops` and `/mcp`.
- **Loopback**: the token is optional unless `serve.require_token = true`. **Non-loopback**: always required.
- **Rejection**: a missing or wrong token gets 401 before the request reaches the registry.
- **The token lives outside the Wiki** (so sync never carries it): `<state dir>/wikirs/<wiki key>/serve-token`, mode 0600, with the same per-Wiki key as the cache dir. It's generated by the first `serve` that needs one.
- **Managing the token**: `wikirs serve --print-token` shows it, and `--rotate-token` replaces it. These are adapter flags, not Operations.
- **`wikirs mcp` over stdio has no auth**: whoever launched the process owns it.

## Host, Origin, CORS

| Check | Rule | On failure |
|---|---|---|
| `Host` | `localhost`, `127.0.0.1` or `[::1]` (with the port), or a name in `serve.allowed_hosts` | 403 |
| `Origin` (when present) | must be in `serve.cors_origins` (empty by default, so no browser page can call the server). Allowed origins get CORS headers | 403 |
| `POST /ops/*` | `Content-Type: application/json` (so cross-site "simple requests" can't get through) | 403 |
| body size | ≤ `serve.max_body` (default 32 MiB, sized for base64 Attachments) | 413 |

There's no rate limiting (single user), and SSE / `watch` connections aren't capped.

## Read-only mode

`serve --read-only` and `mcp --read-only` set the adapter capability `mutations: false`, alongside `local_fs`:

- **MCP** lists only query tools and `rebuild_index` (maintenance never touches a Wiki file). Resources and notifications stay available.
- **HTTP**: `GET /ops` lists only queries and `rebuild_index`, and a mutation call gets 403 `forbidden`. `watch` stays available.

The contract is the same and only the policy differs. The parity test takes the capability into account.

## Transport errors

These rejections happen before any Operation runs, so they aren't part of the closed set of Operation error kinds. They use the same body shape. See [errors.md](errors.md#transport-errors).

## Settings

`[serve]` in the Wiki's [machine settings](wiki-selection.md#machine-settings) holds `bind`, `port`, `require_token`, `allowed_hosts`, `cors_origins`, `read_only` and `max_body`, and flags override it. These settings are per machine, and never go in the committed `config.toml`. The token isn't stored here (see above).
